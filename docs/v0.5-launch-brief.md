## 1. 问题（为什么 v0.5 做这个）

v0.4.0 把对话立成驾驶舱之后，写作输入仍然只有一根吸管：`RunParams` 只有一个 topic 字符串。

1. **意图层缺口**：生成前人的介入为零。用户手里的标题/大纲/思路/资料没处放，全被压进一个字符串「走私」；模型肚子里的猜测顶替了用户意图——文章可以「干净」但注定平庸（门禁保证不烂，保证不了好）。
2. **驾驶舱是聋的**：v0.4.0 的会话历史一个字进不了管线（`llm.ts` 组 prompt 只收 topic）。对话面修好了，意图管道没修。
3. **OD-4 原案治不了本问题**：登记在案的「先确认大纲再写正文」是批准模型的猜测，不是沉淀用户意图——结构意图是三种意图（定位/证据/结构）里最晚、最薄的一层。

## 2. 决策：启动 brief（变密度输入合同）

**一句话是下限，不是标准。** 快路径零损伤（只填主题照跑、agent 不追问）；富路径永远接得住（给多少接多少、给了必须算数）。

| 字段 | 必填 | 绑定级别（合同语义） |
|---|---|---|
| 主题 | ✅ 唯一必填 | 一句话模式 = 只填这个 |
| 标题 | 可选 | **硬绑**——给了就是最终标题，不劳 LLM 另起 |
| 思路 | 可选 | **硬绑**——给了就是文章主张的锚（治无主张写作） |
| 大纲 | 可选 | **骨架绑**——给定节不删不改，管线可补证据节/结尾节 |
| 来源 | 可选 | **硬绑**——给了就必须以可见 URL 写进文章，门禁机械检查「给定 URL 是否以可见文本出现在成文」；AI 不得编造未给来源 |

比内部 series 配方多绑半层（内部大纲完全不绑），但仅当用户主动给大纲时才生效——不罚快路径。

微信外链纪律：外链 `<a>` 会被静默剥离，引用必须以可见文本 URL 呈现——这正好让「来源是否真被用上」机械可验，口径沿用内部已踩坑验证的结论。

## 3. 入口（双门）

1. **对话门（主路径）**：`wewrite_run` 参数扩为 brief 可选字段；agent 从对话自然语言中蒸馏填入（「写一篇 X，思路是 Y，参考这条链接」→ 自动进对应字段）。
2. **工作台门**：启动卡在单行输入下加**默认收起**的「更多信息」折叠区（标题/思路/大纲/来源四框）——产品前门不再只教「一句话」。

行为默认：用户只给一句话时 agent **不追问**、直接跑；至多成稿后提一句「下次可以带思路或链接」。

## 4. 明确不做（v0.5 边界）

- **不拆管线分步**——原子六步不动，所有意图前置于 run 之前（OD-4 的 mid-run 大纲确认路线正式否决）。
- **不加强制问卷门槛**——变密度哲学 = 富输入是奖励，不是过关费。
- **brief 不入库、不系列化**——保存/复用/选题库（向内部 series 生命周期靠拢）是后话，明确推迟。

## 5. 落点（开发时的四处改动清单）

1. 工具签名：`wewrite_run` 扩可选 brief 字段
2. 管线 prompt 语义：draft 锚定思路；outline 步在有大纲时改为「校验+补洞」
3. 新门禁：来源 URL 可见性机械检查（fail 语义与现有 gates 一致：拦默认推送、确认面板可显式覆盖）
4. 启动卡 UI：「更多信息」折叠区

## 6. 前置条件与排期

开发等 v0.4.0 收尾完成后开工：README 截图重拍 + 两项人工验收清账。本文档落地即 v0.5 立项。
